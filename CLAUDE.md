# NYZ

Multiplayer open-world zombie survival game: DayZ + Project Zomboid, with survival mechanics from Ark. Set in New York City at 1:1 scale. Unreal Engine 5, PC first, 250–300 players per server at launch (500 later if budget allows).

## Before doing anything

Read [docs/GDD.md](docs/GDD.md). It is the main source for the game's design.

## Design-doc rules

- Write every design detail the user gives into `docs/GDD.md` in the same turn. Don't summarize detail away; the user wants it kept thorough.
- When a decision is made, changed or reversed, update the GDD **and** add an entry to `docs/DECISIONS.md` with the date and the reason.
- If a new idea conflicts with something already in the GDD, point out the conflict before writing it down.
- Move answered items out of the GDD's "Open questions" section and into the section they belong in.
- **Animations: one master list.** [docs/animations-to-make.md](docs/animations-to-make.md) lists every animation the game needs, for the developer to work through later (a friend by hand, or Higgsfield with Claude; decided 2026-11-13). **Whenever a design adds something a character, zombie, animal or NPC does** (a new item to use, a weapon, a vehicle, an interaction), **add its rows to that list in the same turn**, with the next free ID in its section.
- The GDD holds the agreed high-level design. **Each system gets a deeper design pass when we start building it**; update its GDD section (and the decision log) then.

## Lore rules: nothing gets lost between chats

The developer wants the lore saved in extreme detail. These rules apply to every session.

- **Before any lore discussion, read [docs/lore/LORE.md](docs/lore/LORE.md) in full**, plus the most recent lore entries in `docs/DECISIONS.md`. Don't rely on summaries.
- **Lore stays in this private docs repo (NYZ-DOCs, the developer only).** Never copy lore, `docs/DECISIONS.md` or the transcripts into the game repo (NYZ), which volunteers may get.
- **The lore bible is the home of all lore.** The GDD only gets a spoiler-free summary (§23) and gameplay-facing facts. **The truth and the twist never go in the GDD** (volunteers may read it).
- **Record every lore detail the developer gives in the same turn, in full.** Never summarize it away. For key ideas, **keep the developer's own wording** (quote it), then the cleaned-up version. Note the date and **who proposed it** (developer or Claude).
- **Append every lore message from the developer, verbatim, to [docs/lore/developer-words.md](docs/lore/developer-words.md)**, with a one-line note on what it was answering.
- **Record what was rejected or not chosen, and why**, so ideas aren't re-proposed and can be revisited.
- **Claude's proposals that are still waiting for an answer** go in the lore bible under **"Pending proposals"**, with every option, so they survive if the chat ends before the developer replies. Remove them once answered.
- **Keep the two layers separate and labeled:** *the truth* versus *what survivors believe*.
- **When a lore decision changes earlier lore, update every place it appears** (lore bible, GDD §23, notes on older decision-log entries) and log the change. Search the docs for the old wording to find every place.
- **Check new lore against "What the lore has to explain"** in the lore bible and against earlier decisions; point out conflicts before writing.
- **Check names for real-world clashes** (web search: games, films, books, real drugs and brands) before locking them in, and record the result.
- **Every lore decision also gets a `docs/DECISIONS.md` entry.**
- **End of each lore turn:** tell the developer, in one line, what was recorded and where.
- **Raw transcripts** live in `docs/transcripts/`: the full export (`.zip`, from the app's session export) plus a readable Markdown version made with `python tools/transcript_to_md.py <export.zip> <out.md> "<title>"`. When a question is about *why* something was decided or exactly what the developer said, search the `.md` transcripts. **Offer to export a fresh transcript at the end of any session with substantial design or lore work.**

## Map tooling

- `tools/map/` builds the map border from OpenStreetMap data (needs Python with `shapely`). The segment list at the top of `build_border.py` *is* the border definition; outputs go to `docs/map/`.
- `docs/map/preview.html` opens directly (double-click): it uses Esri's street and satellite tiles. OpenStreetMap's own tiles refuse pages opened from a file, and CARTO's now need a key (both found 2026-11-09).
- **Terrain:** `tools/map/build_terrain.py` builds the heightmap in one command (run with QGIS's Python: `"C:\Program Files\QGIS 4.2.2\bin\o4w_env.bat" && python tools\map\build_terrain.py`), from the USGS 1 m tiles in Downloads, cut to the border; output in `terrain/` (not in git). **Import it with the game repo's `Tools/import_terrain.py`** (command in its header; region by region, resumes after a crash, checks heights), never Unreal's New Landscape import, which holds the whole map in memory. Then `Tools/style_terrain.py` colours it by height and paints the editor's World Partition minimap from the heightmap (about a minute; not Unreal's minimap builder, about two hours here). The process, the tools, and the old September method are in [docs/map/terrain-notes.md](docs/map/terrain-notes.md). The old 40 km terrain lives in NYZv409 (`/Game/FirstPerson/Lvl_FirstPerson`).
- Public Overpass servers are often overloaded; `fetch_routes.py` uses Nominatim plus the main OSM API instead. Python's certificate store fails on these hosts here, so fetching goes through `curl`.

To look around in the editor, the game repo's `Tools/follow_camera.py` (Tools > Execute Python Script; run again to stop) loads everything within `RADIUS_MILES` of the camera as it flies (1 mile since the city's buildings went in, the developer's call; 5 miles took 7 s and about 6 GB of editor memory with the terrain, MN03 and the test block, 2026-11-10). **Never pass `bDisableLoadingOfLastLoadedRegions=True` to a scripted editor run:** on exit it saves the developer's loaded areas as empty (happened 2026-11-10).
- **Dense test block** (GDD §24 milestone 1 point 2): `tools/map/fetch_block.py` (QGIS's Python) fetches the block's outlines into the game repo's `Tools/data/test_block.json`; the game repo's `Tools/build_test_block.py` builds it into `/Game/Maps/NYC` as one `NYZInterior` object per building, with the zombies' room maps (command in its header, about 1–2 minutes; then repackage). Run it with `run_bots.ps1 -Count 40 -Step 10 -Map /Game/Maps/NYC -Start Block` (add `-BlockZombies 200` for zombies in its rooms). The server logs "Test block paths ..." at 10, 30 and 90 s: how many crates are reachable on each floor. To look at it in the editor, run the game repo's `Tools/show_test_block.py` (Tools menu > Execute Python Script; it loads only the block's area and moves the camera there; run it again to unload). The editor's own server program crashed loading the NYC map (the terrain pieces' material fix-up, since resaved with `Tools/resave_terrain.py`; untested since); use the packaged server.
- **Animations** (GDD §25; what clips exist, which are used and what's missing: [docs/animation-list.md](docs/animation-list.md); everything still to be made: [docs/animations-to-make.md](docs/animations-to-make.md)): Epic's free Game Animation Sample, created by the developer as its own project at `Documents\Unreal Projects\GameAnimationSampleZ` (launcher 5.8, 7 GB). Its files are copied into NYZ by the game repo's `Tools/import_animation_sample.py` (run inside the sample project with the launcher editor and `-EnablePlugins=PythonScriptPlugin`; command in its header; about a minute) and stay out of git; then `Tools/make_player_character.py` (NYZ, windowless editor) makes or updates `BP_PlayerCharacter`, takes the transition clips out of the sample's sprint-loop sets (they made straight sprints lose their lean at our 6 m/s; GDD §25) and builds the motion-matching indexes. Movement numbers and keys: Project Settings > Game > NYZ Movement (`Config/DefaultGame.ini`). **Movement test map** `/Game/Maps/MovementTest` (built by `Tools/build_movement_test_map.py`): a course for vaulting and climbing; its header has the windowless `-movementtest` run (alone or against a server), which plays the course like a player and logs each move, server corrections (rubberbanding) and T-pose frames; rerun it after any movement change. **To see a vault or climb frame by frame without the developer recording it:** the game repo's `Tools/capture_move.ps1 -Leg N` (editor closed, needs ffmpeg) plays one leg of that course and tiles a side-on screenshot every 0.1 s into `Saved/MoveCapture/<Tag>.jpg`; `-Set "Key=Value"` tries a NYZ Movement setting for that run. A video the developer sends can be read the same way: `ffmpeg -i <video> -vf "fps=10,tile=4x6" sheet.jpg`. Test movement there: **Play As Client on the NYC map makes the editor's own server load the whole city** (several minutes with the editor unresponsive, about 13 GB; seen 2026-11-11).
- **Load-test map** (`/Game/Maps/LoadTestMap`): rebuilt by `Tools/build_load_test_map.py` in the game repo; the run command is in its header. It runs in an editor with no window (`-ExecutePythonScript`), not as a commandlet, where placing actors fails.
- **Load-test bots:** `powershell -ExecutionPolicy Bypass -File "C:\Game Dev Folder\NYZ\NYZ\Tools\run_bots.ps1" -Count N` (standard test: `-Count 40 -Step 10`; on the city add `-Map /Game/Maps/NYC -Crowd 0`, spawn points from the game repo's `Tools/place_test_starts.py`; a ramp of 1 minute per size that stops itself and prints a line per size; `-Crowd 0` for no hotspot crowds; `-Profile` records an Unreal Insights trace; works from any folder; Windows blocks `.ps1` files by default, and Bypass allows just that run) starts the packaged dedicated server (`NYZServer.exe`, since 2026-11-10; before that the editor program) and N bots running the packaged game (`-bot`); `-Stop` prints the run's server numbers (also added to `Saved/LoadTest/results.txt`) and ends exactly those processes, never the developer's editor. Iris is on (`Config/DefaultEngine.ini`), so the editor must be restarted after that setting changes to join a test server. Logs go to `NYZ/Saved/LoadTest`. After code, content or settings changes, repackage with `-Package` (editor closed: packaging also builds the editor target, which Live Coding blocks); it packages both the game and the dedicated server with the source engine.
- **Zombies** (GDD §8 "Building it"): the city's sleeping zombies (in small groups and roaming hordes, with refill entry points along the wall and at subway entrances, from the MTA's list in `terrain/subway/`) are placed by `tools/map/seed_zombies.py` (QGIS's Python, about a minute) into the game repo's `Data/NYC_zombies.bin` (out of git; rerun after the buildings or border change); one server manager (`NYZZombies`) wakes them near players and moves light zombies (`NYZZombie`); numbers in Project Settings > Game > NYZ Zombies. Console test commands, with `ServerExec` first when joined to a server: `ZombieSpawn 20`, `ZombieCome` (they give chase), `ZombieNoise 60` (a loud noise heard to 60 m), `ZombieClear`. Their plain tinted material is made by `Tools/make_player_character.py`.
- **Noclip while testing:** console `ServerExec ghost` / `ServerExec walk` when joined to a server (development builds allow cheats on every server); plain `ghost` / `walk` in Play without a server.
- **Unreal MCP:** Unreal's built-in MCP plugin (experimental, editor builds only) serves `http://127.0.0.1:18000/mcp` and starts with the editor (per-user setting in `NYZ/Saved/Config/WindowsEditor/EditorPerProjectUserSettings.ini`). Not the default port 8000, which the developer's trading-terminal backend uses. Registered in Claude Code at local scope as `unreal-mcp`. The tools come from the EditorToolset and LiveCodingToolset plugins (enabled 2026-11-08); a session only sees the tools if it started while the editor was running.
